# ADR-0005: Serialize irreversible closure and card writes at the database boundary

## Context

A UI-only or service-only check leaves direct writes and in-flight requests able to modify finalized data. External consumers need a stable boundary with a defined ordering for concurrent closure and mutation.

## Decision

We will enforce irreversible session closure in PostgreSQL, using the session row as the common transaction lock for closure and every card mutation, with triggers guarding direct writes and closed-session reopening or deletion.

## Alternatives Considered

- Disable controls and check status in Python only: rejected because direct database writes and check/write races bypass the freeze.
- Check status in an unlocked trigger: rejected because closure and mutation can observe inconsistent lifecycle ordering.
- Cancel every request that started before closure regardless of commit order: rejected because already committed changes cannot be retroactively uncommitted; the shared lock provides an enforceable transaction boundary.

## Consequences

### Positive

- All application-accessible write paths share one authoritative freeze.
- Concurrent requests have testable semantics: pre-closure commits remain, and writes serialized after closure fail.
- Finalized retrieval can exhaust pagination without card data changing during the read.

### Negative

- Concurrent writes to the same session serialize on a session-row lock.
- Database migrations and real concurrency tests become required for lifecycle changes.
- Closed sessions cannot be corrected or deleted through normal application operations.
