# ADR-0003: Use one server-side push bridge for collaborative views

## Context

The approved architecture assigns subscription ownership to realtime-service, but the previous spec did not build or verify the bridge. Future collaborative features need a single established delivery path.

## Decision

We will route committed Supabase changes through an asynchronous, session-scoped Realtime service in the NiceGUI event loop and deliver browser updates over NiceGUI's existing WebSocket without polling.

## Alternatives Considered

- Periodic database polling: rejected because it adds recurring reads and does not realize the selected push architecture.
- Direct browser subscriptions: rejected because the approved architecture gives subscription ownership to the server-side Realtime service.
- Separate WebSocket gateway: rejected for this increment because it changes the approved topology before the existing event-loop assumption has been tested.

## Consequences

### Positive

- Future collaborative features can reuse session-scoped delivery and lifecycle management.
- Browser delivery and the strict latency requirement receive an independent executable check.

### Negative

- Long-lived asynchronous subscriptions require careful NiceGUI event-loop and disconnection handling.
- The integration check requires live Supabase and browser infrastructure.

## Compliance and Verification

| Rule enforced | Type | Mechanism | Scope |
|---------------|------|-----------|-------|
| Committed changes reach a second same-session browser in less than 2000ms through Supabase Realtime and NiceGUI WebSocket with polling disabled. | DETERMINISTIC | tests/integration/test_realtime.py::test_push_delivery_without_polling | realtime-service and collaborative-canvas |
