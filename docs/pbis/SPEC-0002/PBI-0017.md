# PBI-0017: Add the new migration supabase/migrations/0004_cards_clock_timestamp.sql that replaces public.cards_enforce_integrity() so updated_at on every update and deleted_at on soft-delete are stamped with clock_timestamp() instead of now(). created_at on insert may stay now(). Add an integration test in tests/integration/ using its conftest.py: T1 starts first and holds, T2 updates the same card and commits, then T1 updates the card and commits. T1's committed row must have a later updated_at than T2's, and a connected canvas must show T1's state within 2000ms. The same must hold for a soft-delete's deleted_at.

## Context

Read: `supabase/migrations/0003_cards.sql`

Read the cards_enforce_integrity() definition in 0003_cards.sql to see where now() stamps updated_at and deleted_at. Then read canvas.py::_is_stale to see why a stamp older than the preceding committed version gets a notification discarded. Spec-level acceptance rejected the previous landing because of this. The fix is in version generation only: a second update of the same card waits for the first one's row lock, so clock_timestamp() stamps follow commit order. The Feature Contract's Data Models entry on server-generated timestamps and the DoD item on confirmed operations reaching a second client within 2000ms apply.

## Refinement Protocol

If making committed state reach connected canvases turns out to need a change to canvas.py::_is_stale or to cards.py, or if the Contract's timestamp rules need to change, file a discovery report instead of editing those files or the spec in this PBI. Contract-level changes go through a spec amendment, and a decision about the timestamp strategy goes through an ADR. A code-level fix inside the 0004 migration is handled within this PBI.
